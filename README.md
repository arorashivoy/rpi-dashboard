# Pi Control Room

A small service dashboard for a Raspberry Pi. It uses Python's standard library and static browser files. It has no Python package dependencies.

The dashboard can start or stop configured command-line apps, systemd units, and existing Docker containers. It can also create optional public zrok shares. A share is a separate action from starting an app.

## Requirements

- Raspberry Pi OS with Python 3.9 or newer.
- Docker installed for Docker-managed applications.
- zrok installed and enabled with `zrok enable` for public shares.

## Configure applications

1. Copy the example file to `apps.json`.

   ```sh
   cp apps.example.json apps.json
  chmod 600 apps.json
   ```

2. Edit each entry to match the application installed on the Pi.
3. Set `start` to an argument array for command applications. Do not enter a shell command string.
4. Set `working_dir`, `port`, and optional `url` for each web application.
5. Set `kind` to `systemd` with a `unit`, or `docker` with an existing `container`, when needed.
6. Set `autostart` to `true` only when the application should start with this dashboard.

The example app paths and ports are placeholders. Empty `start` arrays disable command entries until you configure them. A command app stops with `SIGINT` by default, like Ctrl+C. Set `stop.signal` to another signal, or set `stop.command` to an argument array for a custom stop command. The dashboard sends stop signals to the app's process group.

Example command configuration:

```json
{
  "id": "waypoint",
  "name": "Waypoint",
  "kind": "command",
  "working_dir": "/home/pi/apps/waypoint",
  "start": ["npm", "run", "start", "--", "--host", "0.0.0.0"],
  "stop": { "signal": "SIGINT" },
  "port": 3002,
  "url": "http://127.0.0.1:${port}",
  "autostart": false,
  "share": { "mode": "random" }
}
```

For a systemd app, use `"kind": "systemd"` and `"unit": "my-app.service"`. For an existing Docker container, use `"kind": "docker"` and `"container": "my-container"`. The dashboard does not build images or create containers.

## Run the dashboard

```sh
python3 server.py
```

Open `http://127.0.0.1:8787`. Set `RPI_DASHBOARD_PORT` to change the port. The dashboard binds to loopback by default and has no built-in login. Keep it on loopback or use an SSH tunnel for local administration. Do not expose it directly to a network.

For remote administration, keep the dashboard on loopback and use an SSH tunnel:

```sh
ssh -L 8787:127.0.0.1:8787 pi@raspberrypi.local
```

Then open `http://127.0.0.1:8787` on your computer.

To publish the dashboard, let zrok handle visitor authentication. Create a stable public name once, then start this share alongside the dashboard:

```sh
zrok create name pi-dashboard
zrok share public http://127.0.0.1:8787 --name-selection public:pi-dashboard --basic-auth='your-user:use-a-unique-password' --headless
```

Replace the example credentials with a unique pair. zrok requests them before it forwards traffic to the dashboard. Keep both the dashboard and zrok share processes running. For a temporary link, omit `--name-selection public:pi-dashboard`.

## zrok shares

Enable zrok once for the Pi's user account:

```sh
zrok enable
```

Add a `share` object to an application to enable its Share button. A random share uses the public zrok frontend URL generated by zrok. The dashboard reads the URL from zrok's output and displays it. The application must already be running and listening on the configured port. Set `share.basic_auth` to make zrok request a username and password from visitors to that public link.

`zrok enable` authenticates the Pi's zrok CLI account. It does not set visitor credentials. `share.basic_auth` sets the username and password that visitors enter for an individual app link. zrok enforces those credentials before it forwards traffic to the app.

```json
"share": {
  "mode": "random",
  "target": "localhost:3002",
  "basic_auth": { "username": "waypoint-viewer", "password": "use-a-unique-password" }
}
```

The dashboard passes these values to zrok's `--basic-auth` option. This protects the public application share. `apps.json` is excluded from Git because it can contain passwords. Use a unique password for every app share. The zrok CLI receives these credentials as process arguments, which local users with process-inspection access may see.

For a stable public URL with current zrok CLI versions, use `"mode": "named"` and set `share.name`. Create the name once with `zrok create name waypoint`. The Waypoint example uses this mode and selects the public name `public:waypoint`.

```sh
zrok create name waypoint
```

Set `autostart` to `true` so the named share starts when the dashboard starts. Keep this for apps that need a persistent URL, such as Waypoint. Omit `share` for private services such as Pi-hole.

```json
"share": {
  "mode": "named",
  "name": "waypoint",
  "basic_auth": { "username": "waypoint-viewer", "password": "use-a-unique-password" },
  "autostart": true
}
```

The dashboard invokes `zrok share public --headless localhost:PORT` for a random share. For a named share, it adds `--name-selection public:NAME`. It adds the configured `--basic-auth=username:password` option to public-share commands. For older reserved-share configurations, use `"mode": "reserved"` with a `token`. If your installed zrok version needs different arguments, set `share.command` to its exact argument array. Treat reservation tokens and passwords as credentials. Keep `apps.json` mode `600` and do not publish it.

## Start at boot

Install the project in a stable path on the Pi, such as `/opt/rpi-dashboard`, and copy your configured `apps.json` there. Create `/etc/systemd/system/rpi-dashboard.service`:

```ini
[Unit]
Description=Raspberry Pi service dashboard
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=pi
WorkingDirectory=/opt/rpi-dashboard
ExecStart=/usr/bin/python3 /opt/rpi-dashboard/server.py
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```

Enable the dashboard at boot. Any app with `autostart: true` and any share with `share.autostart: true` also start when the dashboard starts.

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now rpi-dashboard.service
sudo systemctl status rpi-dashboard.service
```

For Docker control, add the `pi` user to the Docker group or run the dashboard with a suitable service account. Group membership grants broad control over the host; review that access before enabling it.

## Configuration reference

- `id`: unique letters, numbers, `_`, or `-`.
- `kind`: `command` (default), `systemd`, or `docker`.
- `start`: executable and arguments for a command app.
- `stop.signal`: process signal for a command app; defaults to `SIGINT`.
- `stop.command`: optional executable and arguments that replace signal-based stopping.
- `port` and `url`: local endpoint shown in the dashboard.
- `share.mode`: `random` or `reserved`.
- `share.mode`: `named` for a stable public name on current zrok CLI versions.
- `share.name`: public name used by `named` mode. Create it once with `zrok create name NAME`.
- `share.basic_auth`: optional visitor username and password for public links.
- `share.target`: optional target override, such as `localhost:3002`.
- `share.autostart`: starts the share with the dashboard.
- `share.command`: optional complete zrok argument array for CLI compatibility.

The dashboard polls service state every five seconds. Process apps started by the dashboard are tracked while it runs; systemd and Docker states are checked through their native CLIs.
